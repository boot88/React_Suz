## Удобство админ-панели

В `/settings` личные параметры заявки, языка, темы и тестового режима собраны в «Мои настройки». Общий лимит вложений находится в «Настройки программы» и применяется только после сохранения. Обновление справочников и резервные копии находятся в «Обслуживание и резервные копии»; подписи объясняют область действия операций.

Дополнительная строка быстрых фильтров удалена; сохранены исходные карточки статистики и фильтр периода. В карточке сверху расположены название, статус, исполнитель и действия; подробная хронология раскрывается по нажатию.

Поиск сотрудников позволяет одновременно выбрать отдел и искать по ФИО, кабинету, телефону или другому полю. Сервер объединяет условия через AND; отдел сравнивается точно. Поиск только по отделу и прежний поиск без отдела также доступны.

Основная кнопка экспорта называется «Экспорт в Excel»; она выгружает все найденные заявки с учётом поиска и применённого периода. Кнопка «Сбросить период» в раскрываемых фильтрах убрана. Выбранные строки экспортируются отдельной кнопкой с их количеством; при переходе к другому набору строк выбор сбрасывается. Неприменённые даты не влияют на экспорт.

Статьи базы знаний сначала показывают заголовок, категорию и короткий текст. Полное решение и фотографии открываются кнопкой «Читать решение».

Экспорт, импорт и обновление справочников показывают фактические этапы без расчётных процентов. Перед восстановлением сервер проверяет копию и возвращает только метаданные (`POST /api/backups/:group/inspect`): раздел, количество записей, файлов и фотографий в статьях. Окно подтверждения также показывает имя и размер файла и дату создания, если она есть в копии. SQL-копии прежнего формата не содержат даты создания; интерфейс сообщает об этом. Только после подтверждения выполняется прежний транзакционный импорт с резервированием текущего состояния.

Статистика сравнивает два соседних интервала одинаковой длительности: поступления по дате подачи, окончательные закрытия по дате закрытия (в том числе ранее созданных заявок), остаток и его изменение. Выбор исполнителей применяется к обоим интервалам. Остаток учитывает заявки до окончательного закрытия, включая повторно открытые этапы. Записи без корректных дат исключаются из сравнения с явным уведомлением. Для «Всё время» предлагается выбрать ограниченный период; диапазоны отображаются по времени Новосибирска. График сохраняет открытие конкретных заявок.

Успех, ошибки и предупреждения в админке используют общий компонент `AdminNotice` с единым оформлением и доступными ролями status/alert. Уведомления базы знаний и редактирования заявок показываются внутри страницы вместо браузерных alert. Диалоги подтверждения удаления сохранены.

## RU/EN в админ-панели

Дашборд, карточка и редактирование заявки, новая заявка, справочник сотрудников, база знаний, диагностика сети, статистика и настройки используют перевод при отрисовке React. Переводятся подписи, фильтры, подсказки, ошибки формы, окна подтверждения и сообщения операций. При переключении RU/EN открытые формы, фильтры и счётчики сохраняются. ФИО, пользовательские описания и комментарии, а также значения категорий в API и SQL не переводятся. Даты и подписи графиков используют выбранную локаль с прежней таймзоной. Страница «Поиск документов» `/chat-tools/audit` также переводит периоды, архивы, просмотр файлов, подтверждения и ошибки. Обычный чат сохраняет свой механизм перевода.

## Персональные настройки и первоначальный вид

Новый пользователь получает Service/English на входе, новый дизайн чата, светлые темы, обычную плотность и обычный размер текста. В админке включён новый вид карточек заявок; промежуточная таблица редактирования, история действий в карточке и тестовый режим выключены. Профиль содержит фиксированную ссылку «НИОХ СО РАН» на https://web3.nioch.nsc.ru/nioch/index.php/ru/; выбор версии сайта убран.

Язык входа, чата и админки — один персональный параметр. Явный выбор RU/EN перед входом сохраняется вместе с успешной авторизацией. Уже выбранные пользователем настройки сохраняются; значения по умолчанию используются для отсутствующих параметров. Настройки админки больше не наследуются от другого аккаунта на этом компьютере. При повторном входе на другом устройстве они загружаются из SQL. Частичные обновления чата и админки объединяются, не стирая остальные настройки. При сетевой ошибке изменения остаются в персональной очереди, отображается ошибка сохранения и выполняется повтор. Перед выходом отправляются оставшиеся изменения.

## Рассылка сотрудникам

Администратор открывает «Рассылка» в чате или «Рассылка сотрудникам» в меню админки. Можно выбрать всех сотрудников либо несколько человек через поиск по ФИО и галочки. Перед отправкой показываются количество получателей, текст и число файлов; требуется подтверждение. Каждому приходит отдельное сообщение с отметкой «Рассылка» в личном диалоге с администратором. Ответы остаются в этом диалоге.

История отправителя показывает дату, текст, вложения, получателей, доставку и прочтение. «Доставлено» означает сохранение сообщения в базе для получателя, включая сотрудников офлайн. Повтор отправляет только недоставленные сообщения. Сообщение, ссылки на его файлы и статус получателя сохраняются транзакционно; повтор запроса после обрыва соединения не создаёт дубликаты. Неподтверждённый запрос сохраняется в браузере до проверки результата или безопасного повтора. В архивный диалог рассылка не отправляется: его нужно сначала восстановить, затем повторить доставку.

Таблицы `chat_broadcasts` и `chat_broadcast_recipients` создаются автоматически и входят в резервную копию чата. Рассылка и её история доступны только администраторам; историю видит её отправитель.

## Файлы в чате и ленте

Сотрудники могут отправлять файлы с любым расширением или без него: музыку, документы, ZIP/RAR/7z и другие архивы, спектры и файлы приборов. Неизвестный браузеру тип не блокирует загрузку. Содержимое передаётся без преобразования; действует сохранённый администратором лимит размера на файл. Фото и видео поддерживают просмотр, остальные форматы можно скачать. HTML, SVG и другие активные форматы выдаются как скачиваемые файлы. При настроенной антивирусной проверке она продолжает работать.

## Резервные копии в настройках администратора

В `/settings` администраторы могут экспортировать и восстановить:

- заявки (`application`, `application_events`, `application_views`) в SQL;
- базу знаний (`knowledge_base`) в SQL, включая base64-фотографии;
- учётные записи, пароли, профили, аватары и уведомления менеджера;
- чат, ленту, комментарии, реакции, вложения, архивы, аудит и журнал восстановления сообщений;
- настройки сервера (`app_settings`), включая лимит размера вложений, в SQL;
- дополнительные локальные таблицы, обнаруженные в текущей базе;
- все локальные данные одним архивом;
- настройки интерфейса текущего пользователя отдельным JSON-файлом.

`phone_book` и `network_map_snapshot` восстанавливаются обновлением из внешних источников и не входят в копии. `auth_sessions` не экспортируется; восстановление учётных записей завершает действующие сессии. `.env`, параметры подключения к внешним источникам, присутствие пользователей, токены, кеши и черновики браузера не переносятся. Настройки языка, темы, списка и карточки заявок сохраняются для каждой учётной записи в `employee_profiles.profile_json.preferences` и входят в копии профилей. Браузер хранит персональный кеш и очередь ещё не отправленных изменений.

Заявки и база знаний сохраняются как обычный MySQL SQL-дамп. Архивы с файлами имеют расширение `.suz.gz` (gzip JSON, внутри SQL и файлы с контрольными суммами). Встроенный импорт принимает только копии своего формата и проверяет контрольные суммы, раздел, таблицы, колонки и пути **до замены данных**; SQL из загрузки не выполняется. Значения передаются параметрами. SQL можно также использовать в инструментах MySQL. На новом сервере обычные таблицы создаются из проверенных метаданных копии; схемы с внешними ключами, вычисляемыми колонками или сложными индексами нужно подготовить миграциями. Таблицы должны использовать InnoDB.

Импорт полностью заменяет таблицы и файлы выбранного раздела, включая очистку файлов и сегментов журнала, отсутствующих в копии. Перед заменой сервер сохраняет прежнее состояние в `server/data/admin-restore-recovery`; в интерфейсе появляется кнопка скачивания этой копии. При обычной ошибке записи SQL откатывается, заменённые файлы возвращаются. При аварийном завершении процесса восстановите данные из сохранённой копии прежнего состояния; не удаляйте каталог `restore-*`, если возникла ошибка отката файлов. Копии содержат персональные данные и пароли в сохранённом сервером виде; они доступны только администраторам и не публикуются статическим сервером. Старые копии на сервере удаляются вручную.

Во время операции сервер приостанавливает API-запросы и ждёт завершения текущих операций (до 30 секунд). Это блокировка одного процесса: при нескольких экземплярах сервера сначала остановите остальные экземпляры и фоновые задания, работающие с той же БД или файлами. После восстановления обновите страницу; при восстановлении учётных записей войдите снова. Вложения заявок, созданных из чата, входят в копию чата или общую копию.

Одна копия ограничена 512 МБ в распакованном виде, вложения — 256 МБ; крупные наборы экспортируйте отдельными разделами или используйте серверные инструменты резервирования. На HTTPS и localhost поддерживаемые браузеры открывают выбор места сохранения. В остальных случаях используется обычная загрузка браузера: включите «Всегда указывать место для скачивания» в его настройках, чтобы выбирать папку.

## Чат сотрудников `/employee`

В профиле, в блоке оформления, добавлены «Дизайн чата → Текущий / Новый» и отдельный язык интерфейса. Текущий дизайн остаётся выбранным по умолчанию. Настройки сохраняются локально и в профиле на сервере. Новый дизайн показывает последние диалоги, закреплённые сверху, отдельный справочник «Новый диалог» и один рабочий экран на телефоне.

Отправка использует сохраняемую очередь: сетевые ошибки повторяются с увеличением интервала до 60 секунд, остальные ошибки требуют явного повтора или редактирования сообщения. По умолчанию вложения ограничены 10 МБ на файл. Администратор может задать целое число от 10 до 150 МБ в `/settings` и нажать «Сохранить»: лимит хранится в SQL, сохраняется после перезапуска и применяется к новым загрузкам всех сотрудников в чате и ленте. Изменение поля без сохранения не меняет действующий лимит. На сообщение разрешено до 10 файлов; загрузка и отмена привязаны к исходному диалогу. История использует составной курсор и виртуализированный список. Счётчики непрочитанных и отметки прочтения поступают с сервера; после подключения SSE загруженные сообщения сверяются с сервером.

Административные инструменты сотрудников, аудита и архивов находятся в админке: `/chat-tools/employees`, `/chat-tools/audit`, `/chat-tools/archive`. Полноэкранный чат и кнопка возврата в админку сохранены.

### Обновление сервера и сессии

Клиент и сервер этого изменения следует обновлять вместе: запись массива переписки целиком заменена операцией `/threads/:id/clear`, добавлены пакетные медиатокены и сверка сообщений.

При первом входе сервер создаёт таблицу `auth_sessions`; пользователю базы нужны права `CREATE TABLE`. После обновления ранее выданные токены перестают действовать — потребуется повторный вход. Удаление аккаунта, смена пароля или роли прекращают доступ старой сессии. Открытые SSE-потоки завершаются при истечении токена; изменения аккаунта проверяются также каждые 15 секунд. Уже выданные токены отдельных файлов имеют отдельный срок действия до 10 минут.

### Журнал восстановления сообщений

MySQL остаётся основным хранилищем. Вместо полной перезаписи JSON при каждом сообщении сервер дописывает изменения в `server/data/backups/message-journal/YYYY-MM-DD.jsonl`. Сохраняйте этот каталог вместе с резервной копией базы и каталогом загрузок. Ошибки записи журнала выводятся в серверный лог; журнал не заменяет резервное копирование MySQL.

Для восстановления отсутствующих или более старых записей из журнала: `npm run recover:chat-journal`. Выполняйте восстановление в техническое окно, остановив запись сообщений другими процессами. Восстановление через раздел архивов также учитывает старые JSON-снимки. Маркеры окончательного удаления не позволяют повторно импортировать старые записи удалённой переписки; их нужно сохранять вместе с журналом. Утилита прекращает работу при повреждённой строке журнала, чтобы не скрывать потерю данных.

Журнал не удаляется автоматически: срок хранения и перенос старых файлов следует согласовать с политикой резервных копий. Перед удалением части журнала нужны проверенная полная копия базы и сохранённые маркеры окончательного удаления.

## MySQL

Сервер использует только MySQL/MariaDB через `mysql2`. Для production можно передать одну строку подключения:

```env
MYSQL_URL=mysql://user:password@host:3306/database
```

Либо отдельные переменные:

```env
DB_HOST=mysql-host
DB_PORT=3306
DB_NAME=its
DB_USER=mysql-user
DB_PASSWORD=mysql-password
```

Также поддерживаются стандартные переменные `MYSQLHOST`, `MYSQLPORT`, `MYSQLDATABASE`, `MYSQLUSER` и `MYSQLPASSWORD`. Если провайдер требует TLS, добавьте `DB_SSL=true`.

Для локального запуска скопируйте `.env.example` в `.env`, укажите пароль MySQL и перезапустите `npm run dev`. Файл `.env` не попадает в Git.

После первого обновления выполните один раз:

```bash
npm run migrate:chat-storage
```

Команда переносит старые сообщения и вложения из JSON/BLOB на MySQL и диск, а также заполняет индекс доступа «сообщение — файл». Обычное открытие чата эту миграцию не запускает.

## Восстановление пароля

Отправка через email отключена.  
При `POST /api/auth/forgot-password` создаётся новый временный пароль и формируется служебное уведомление менеджерам (хранится в `server/data/managerNotifications.json`) и системное сообщение в MySQL-чате менеджера/сотрудника.

Админка: поиск заявок выполняется через 300 мс после ввода, предыдущие запросы отменяются; даты применяются только кнопкой применения периода. Счётчики меню не опрашивают сервер в скрытой вкладке и объединяют пересекающиеся обновления. Сохранение статьи блокирует повторное нажатие до завершения запроса. Переходы между разделами используют появление за 180 мс и учитывают prefers-reduced-motion.

Статистика получает сгруппированные данные через `/api/application-statistics`, без выгрузки полной истории на клиент. Сравнение периодов рассчитывается SQL-агрегациями; списки заявок за день запрашиваются через `/api/application-statistics/day` порциями по 100. Для этой версии необходимо обновить и клиент, и сервер.


## Обновление административной панели (октябрь 2026)

Клиент и сервер этой версии нужно обновлять вместе. Поля `application.revision` и `users.must_change_password`, а также индексы заявок подготавливаются автоматически при первом обращении; учётной записи MySQL нужны права ALTER/CREATE INDEX. Старые формы редактирования без версии отклоняются с 409, поэтому после обновления открытые формы нужно перезагрузить.

Список получает события `/api/applications/stream`; после разрыва соединения включается резервное обновление раз в 30 секунд. Фильтры, страница, прокрутка и черновики сохраняются в текущем браузере на время сессии вкладки. Сохранение проверяет версию заявки под блокировкой строки. Повторное назначение исполнителя и подтверждение закрытия не перезапускают время работы. Дневные фильтры используют UTC-время `created_at` с границами календарного дня Новосибирска.

Excel создаётся запросом GET `/api/applications/export-xlsx` с фильтрами или `ids`; передавать массив заявок из браузера больше не нужно. Лимит — 100 000 строк. База знаний возвращает страницы кратких результатов; полный текст и фотографии загружаются при раскрытии. Допустимы JPEG, PNG, GIF и WebP: до 2 МБ на файл, 20 изображений и 10 МБ JSON-данных изображений на статью.

Новые административные аккаунты при синхронизации получают индивидуальный случайный временный пароль и обязательную смену при первом входе. Пароли существующих аккаунтов сохраняются. Временные пароли показывает отчёт синхронизации; если ответ потерян, повторная синхронизация возвращает ещё не использованные пароли. При первоначальном заполнении пустой базы их может получить оператор сервера из `server/data/initial-admin-credentials.json` (права 0600). После смены пароля соответствующая запись удаляется. Этот файл нельзя публиковать или добавлять в Git.

SQL-экспорт резервных копий формируется потоково во временный файл с контрольной суммой. При экспорте чтение остаётся доступным, изменения приостанавливаются. Восстановление блокирует работу с данными, вставляет строки пакетами и сохраняет прежнюю копию. Действующие формы после восстановления получают конфликт версии. Упакованные копии с файлами и предварительная копия перед восстановлением пока собираются в памяти; общий лимит остаётся 512 МБ. Для нескольких серверных процессов необходимо остановить остальные экземпляры на время копирования/восстановления: блокировка обслуживания действует внутри одного процесса.

`tools/run-dev.sh` передаёт клиенту выбранный порт тестового API, чтобы тестовая копия не обращалась к серверу на боевом порту 5000. Замеры запросов на настоящей MySQL-базе и проверка восстановления на копии рабочих данных должны выполняться перед развёртыванием. Тесты маршрутов в репозитории используют подставную базу и не меняют рабочие записи.

## Боевой адрес: порт 3000, доп. порт 5000 и имена esz / zayavki

Боевая версия работает на сервере hund03 (`192.168.129.31`). Служба слушает все
сетевые адреса машины, поэтому один и тот же сайт открывается по любому её адресу:

| Адрес | Назначение |
| --- | --- |
| `http://192.168.129.31:3000/` | основной адрес, работает всегда и везде |
| `http://192.168.129.31:5000/` | доп. порт для старых ссылок и закладок |
| `http://zayavki.nioch.nsc.ru:3000/` | штатное DNS-имя зоны НИОХ, работает отовсюду |
| `http://esz:3000/` | короткое имя, работает из клиентской сети НИОХ |
| `http://el-ap-sys:3000/` | запасное имя (запись в hosts клиента, если DNS не помогает) |
| `http://esz/`, `http://zayavki.nioch.nsc.ru/` | те же адреса без порта — после включения виртуалхоста Apache (см. ниже) |

Оба DNS-имени уже настроены и правок на клиентах не требуют:

* `zayavki.nioch.nsc.ru` → `192.168.129.31` — запись в зоне `nioch.nsc.ru`
  (проверено с hund09 и с hund03);
* `esz` → `192.168.129.31` — короткая запись на клиентском DNS-сервере
  `192.168.1.1` (проверено с hund09), поэтому имя `esz` пишется без домена.

Чтобы короткое имя работало и из серверной сети, и в официальном виде, у
администраторов DNS имеет смысл попросить две записи:

```
esz.nioch.nsc.ru.            IN A   192.168.129.31
31.129.168.192.in-addr.arpa. IN PTR esz.nioch.nsc.ru.
```

(сейчас обратная запись `192.168.129.31` указывает на `esz.` — без домена; на
вход это не влияет). Устаревшая запись `hund03.nioch.nsc.ru` ведёт на
`192.168.129.98` — нерабочий адрес, её тоже полезно поправить.

Сетевой адрес у hund03 один — `192.168.129.31`. Компьютеры из других сетей
(например, hund09 = `192.168.1.35` из сети `192.168.1.0/24`) доходят до него
через свой шлюз `192.168.1.1`, поэтому второй адрес серверу не нужен.

### Адрес без порта: `http://esz/` вместо `http://esz:3000/`

Номер порта из адреса убрать можно, и приложение для этого менять не нужно: на
hund03 уже работает Apache и слушает порт 80 (сейчас он отдаёт только служебную
страницу-заглушку «It works»). Добавляется виртуалхост-прокси, который по именам
передаёт запросы приложению на порт 3000. Включается одной командой от root:

```bash
ssh -t qwest@192.168.129.31 'sudo bash ~/React_Suz/tools/hund03-port80-proxy.sh'
```

После этого открываются адреса без порта: `http://esz/`,
`http://zayavki.nioch.nsc.ru/`, а когда появятся записи в DNS — также
`http://esz.nioch.nsc.ru/` и `http://el-ap-sys/`.

Что важно:

* сборку и настройки клиентов менять не нужно — клиент обращается к `/api`
  относительным путём, поэтому адрес с портом и без порта одинаково рабочие;
* прежние адреса `http://192.168.129.31:3000/`, `:5000` и имена с портом
  продолжают работать: служба react-suz и её порты не изменяются;
* порт 80 по IP не затронут: страница-заглушка Apache, `/webmail` и
  `/phpMyAdmin` открываются как раньше. Если нужно, чтобы и
  `http://192.168.129.31/` открывал приложение, запустите скрипт с ключом
  `--with-ip` — тогда `/webmail` и `/phpMyAdmin` останутся на месте, а всё
  остальное уйдёт в приложение;
* убрать всё назад: та же команда с `--remove`.

Скрипт `tools/hund03-port80-proxy.sh` создаёт
`/etc/apache2/sites-available/react-suz.conf`, включает модули `proxy` и
`proxy_http`, подключает сайт, проверяет конфигурацию (`apache2ctl configtest`) и
перезагружает Apache. Повторный запуск безопасен, файл конфигурации пишется заново.

### Если имя не открывается, а по IP всё работает

Почти всегда причина в одном: браузер ходит через VPN или прокси. Тогда имя
уходит на DNS VPN-провайдера и не разрешается, а адрес по IP открывается
напрямую. Лечится списком обхода: браузер должен обращаться к внутренним
адресам мимо прокси.

Chrome — нужен запуск с флагом (браузер закрыть и открыть заново):

```bash
google-chrome --proxy-server=socks5://127.0.0.1:10808 \
  --proxy-bypass-list="localhost;127.0.0.1;192.168.0.0/16;10.0.0.0/8;*.local;*.nsc.ru;esz;zayavki;el-ap-sys"
```

В VPN-лаунчере hund09 (`~/.local/share/xray-vpn/vpn.sh`) это уже прописано:
переменная `SITE_DIRECT` со списком имён и локальных сетей передаётся Chrome и
VS Code как `--proxy-bypass-list`, а режим «весь трафик» получает те же имена в
`ignore-hosts` (GNOME) и `NO_PROXY`. Если VPN включён, Chrome надо открывать
значком «Chrome через VPN», а не обычным — флаг прокси действует только при
старте браузера.

Тем, у кого имя не работает, проверку делают на их компьютере: `nslookup esz`
должен вернуть `192.168.129.31`. Если нет — имя задают в hosts (скрипты ниже)
или правят DNS.

Клиент и API отдаёт один процесс (`npm start` из службы `react-suz`), поэтому адрес
в браузере можно менять свободно: сборка использует абсолютные пути `/static/...`
(`"homepage": "/"` в `package.json`), а клиент обращается к API по относительному
`/api` (`src/utils/apiConfig.js`). Пересборка при смене адреса или имени не нужна.

Автозапуск: служба `react-suz` включена (`systemctl --user enable`) и linger включён
(`loginctl show-user qwest` → `Linger=yes`), поэтому при включении hund03 приложение
поднимается само, без входа в систему, и сразу отвечают оба порта.

### Вход в систему и доступ по источнику (CORS)

Вход в панель `/admin` и в чат выполняется запросом `POST /api/auth/login`. Браузер
присылает заголовок `Origin` даже тогда, когда страница обращается к тому же самому
серверу, поэтому источником считается и собственный адрес сайта: адрес из адресной
строки должен совпадать с заголовком `Host` запроса. Благодаря этому вход работает
одинаково и по `http://192.168.129.31:3000`, и по `:5000`, и по `http://esz:3000`,
и по `http://el-ap-sys:3000`, и по `http://zayavki.nioch.nsc.ru:3000` — без
дополнительных настроек.

Правило живёт в `server/utils/corsPolicy.js`, тесты — в `server/utils/corsPolicy.test.js`
(`npm run test:server`). Признак прежней ошибки: служба отвечала `500` на вход
(«Произошла внутренняя ошибка сервера»), а в `~/react-suz.log` была строка
`CORS origin is not allowed`; при этом форма показывала неверный пароль при верных
данных. Если появится отдельный фронтенд на другом адресе, его источник перечисляется
в `.env` через запятую: `CORS_ORIGINS=http://192.168.129.31:3000,https://friend.example`.

### Запасной способ: имена в файле hosts (tools/setup-client-name.*)

Если DNS в конкретной сети не знает имён, они задаются в файле hosts на
компьютере пользователя. Один скрипт сразу прописывает три имени: `esz`,
`zayavki`, `el-ap-sys` (список задаётся параметром). Права root на сервере,
настройка DNS или Apache для этого не нужны.

Windows — двойной щелчок по `tools\setup-client-name.cmd` (права администратора
запрашиваются сами) или вручную в PowerShell от имени администратора:

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\setup-client-name.ps1
powershell -ExecutionPolicy Bypass -File .\tools\setup-client-name.ps1 -Names esz,zayavki
powershell -ExecutionPolicy Bypass -File .\tools\setup-client-name.ps1 -Remove
```

Linux/macOS:

```bash
sudo bash tools/setup-client-name.sh
sudo APP_HOST_NAMES="esz zayavki" bash tools/setup-client-name.sh   # свои имена
sudo bash tools/setup-client-name.sh --remove
```

Скрипты безопасно запускать повторно: записи обновляются, а не дублируются.
Проверка без изменения системных файлов:

```bash
DRY_RUN=1 HOSTS_FILE=/tmp/hosts-test bash tools/setup-client-name.sh
```

Если у сервера когда-нибудь появится ещё один адрес, скрипт примет сразу оба:
приложение слушает все интерфейсы машины, а `APP_HOST_IPS` (в PowerShell — `-Ip`)
принимает список адресов через пробел.
